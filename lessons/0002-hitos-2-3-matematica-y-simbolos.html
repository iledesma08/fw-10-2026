Hitos 2 y 3: matemática entera y símbolos definidos

Al terminar vas a poder recorrer las cuatro funciones de mathlib con una entrada chica y explicar por qué nm build/lib/mathlib.o las muestra como T, no como U.

1. Cuatro funciones y una demo

El hito 2 pide math_factorial y math_gcd. El hito 3 agrega math_isqrt y math_is_prime. Las cuatro viven en src/lib/mathlib.c; sus prototipos están en src/lib/mathlib.h, y src/demo/demo_math.c las usa para imprimir resultados.

Archivos y responsabilidades
ArchivoQué aporta y qué no aporta
mathlib.hAporta los prototipos de las cuatro funciones y la definición static inline de bit_set; no aporta los cuerpos de factorial, GCD, raíz y primalidad.
mathlib.cAporta las definiciones globales de las cuatro funciones; no aporta la salida por consola.
demo_math.cAporta las llamadas, conversiones y textos de la demo; no aporta la implementación de las operaciones.

Dentro de ese reparto, la tabla siguiente resume qué hace cada operación:

Qué hace cada función
FunciónRecibe y devuelve
math_factorialRecibe int32_t n; devuelve n!, o 0 si n < 0. Producto iterativo desde 2.
math_gcdRecibe int32_t a y b; devuelve el Máximo Común Divisor: gcd(|a|, |b|). Algoritmo de Euclides.
math_isqrtRecibe uint32_t n; devuelve la parte entera de sqrt(n). Aproximaciones enteras de Newton.
math_is_primeRecibe int32_t n; devuelve 1 si es primo y 0 si no. Prueba candidatos 6k ± 1.

Hay una excepción que conviene recordar: mathlib.h declara las cuatro funciones, pero también contiene el cuerpo static inline de bit_set (líneas 49–51). Es decir, un header no siempre contiene solo declaraciones; en este TP, print.h sí contiene solo prototipos, mientras que mathlib.h mezcla prototipos y una definición inline. bit_set se usa en otros hitos, no en estas cuatro funciones matemáticas.

Fidelidad del Makefile

El README del hito 2 pide agregar mathlib.c a SRCS. En el Makefile final, mathlib.c aparece dentro de LIB_SRCS porque el hito 11 lo mueve a libutils.a. El objeto sigue siendo build/lib/mathlib.o.

2. Factorial: un acumulador y dos casos borde

int32_t math_factorial(int32_t n) {       // mathlib.c:8
  int32_t result = 1;                     // mathlib.c:9

  if (n < 0)                              // mathlib.c:11
    return 0;                             // mathlib.c:12

  for (int32_t i = 2; i <= n; i++)        // mathlib.c:14
    result *= i;                          // mathlib.c:15

  return result;                          // mathlib.c:17
}

El recorrido es corto:

  • result empieza en 1, que es el neutro del producto.
  • Si n es negativo, la función devuelve 0 antes de entrar al bucle.
  • El bucle empieza en i = 2 y multiplica mientras i <= n. Para n = 0 o n = 1 no entra ninguna vez; por eso 0! y 1! devuelven 1.
  • Para n = 5: result pasa por 2, 6, 24 y 120.
Un límite real

El comentario del header dice que la función «se desborda silenciosamente» para valores grandes. Eso describe el comportamiento esperado en esta implementación, pero el desbordamiento de un entero con signo no es una garantía del lenguaje C. Para la defensa alcanza con decir que el resultado deja de ser confiable cuando n! no cabe en int32_t; no hace falta convertir la demo en una biblioteca de precisión arbitraria.

3. GCD: Máximo Común Divisor con el algoritmo de Euclides

int32_t math_gcd(int32_t a, int32_t b) {  // mathlib.c:20
  if (a < 0)                               // mathlib.c:21
    a = -a;                                // mathlib.c:22
  if (b < 0)                               // mathlib.c:23
    b = -b;                                // mathlib.c:24

  while (b != 0) {                         // mathlib.c:26
    int32_t tmp = b;                       // mathlib.c:27
    b = a % b;                             // mathlib.c:28
    a = tmp;                               // mathlib.c:29
  }

  return a;                                // mathlib.c:32
}

La función calcula el Máximo Común Divisor (GCD, por sus siglas en inglés Greatest Common Divisor). Primero se ignoran los signos: si a o b son negativos, se les cambia el signo. Después, el bucle hace siempre lo mismo: guarda el divisor actual en tmp, calcula el resto en b y mueve el divisor anterior a a. Cuando el resto llega a cero, el último divisor no nulo quedó en a; ese es el Máximo Común Divisor.

Traza de math_gcd(48, 18)
Inicio de vueltatmpNuevo bNuevo a
a = 48, b = 181848 % 18 = 1218
a = 18, b = 121218 % 12 = 612
a = 12, b = 6612 % 6 = 06
a = 6, b = 0—El bucle no entraDevuelve 6

Los ejemplos de la demo son seguros. No se analizan acá todos los extremos de int32_t, como el cambio de signo de INT32_MIN; eso excede el objetivo del hito.

4. Raíz entera: aproximaciones de Newton

uint32_t math_isqrt(uint32_t n) {         // mathlib.c:35
  uint32_t x;
  uint32_t y;

  if (n == 0)                              // mathlib.c:39
    return 0;                              // mathlib.c:40

  x = n;                                   // mathlib.c:43
  y = (x + 1) / 2;                         // mathlib.c:44
  while (y < x) {                           // mathlib.c:45
    x = y;                                  // mathlib.c:46
    y = (x + n / x) / 2;                   // mathlib.c:47
  }

  return x;                                // mathlib.c:50
}

Para n = 0 devuelve 0. Para el resto, empieza con x = n e y = (n + 1) / 2, y repite la aproximación de Newton mientras la nueva y sea menor que x. La división es entera, así que se descarta la parte fraccionaria en cada paso. Cuando y deja de bajar, x ya es la parte entera de la raíz.

Traza de math_isqrt(17)
xy calculada¿Sigue el bucle?
17(17 + 1) / 2 = 9Sí: 9 < 17
9(9 + 17 / 9) / 2 = 5Sí: 5 < 9
5(5 + 17 / 5) / 2 = 4Sí: 4 < 5
4(4 + 17 / 4) / 2 = 4No: 4 < 4 es falso

La función devuelve 4, que es la parte entera de sqrt(17). No devuelve una aproximación con decimales ni la primera aproximación mayor que la raíz.

5. Primalidad: probar candidatos, no todos

int math_is_prime(int32_t n) {            // mathlib.c:53
  if (n < 2)                               // mathlib.c:54
    return 0;                              // mathlib.c:55
  if (n < 4)                               // mathlib.c:56
    return 1;                              // mathlib.c:57
  if (n % 2 == 0 || n % 3 == 0)            // mathlib.c:58
    return 0;                              // mathlib.c:59

  for (int32_t i = 5; (int64_t)i * i <= n; i += 6) {  // mathlib.c:61
    if (n % i == 0 || n % (i + 2) == 0)    // mathlib.c:62
      return 0;                            // mathlib.c:63
  }

  return 1;                                // mathlib.c:66
}

Leída por casos:

  • n < 2 no es primo: incluye negativos, cero y uno.
  • 2 y 3 son primos; por eso n < 4 devuelve 1 después de descartar los menores que dos.
  • Si n es par o múltiplo de tres, no es primo (salvo los casos anteriores, que ya se resolvieron).
  • El bucle empieza en 5, avanza de seis en seis y prueba i y i + 2: 5 y 7, 11 y 13, 17 y 19, etc. La condición i * i <= n corta cuando ya se probaron todos los divisores posibles.
  • El cast a int64_t se hace antes de multiplicar: si i fuera int32_t, el producto podría desbordarse antes de compararlo con n.

Los candidatos 6k ± 1 son los únicos que pueden ser primos después de descartar 2 y 3, pero no todos son primos. Por ejemplo, 25 = 6 · 4 + 1 y, sin embargo, 25 % 5 == 0. La función no supone que el candidato sea primo: lo prueba con %.

6. La salida de la demo

La demo imprime los resultados con print_str y print_dec, no con printf. El hito 2 pide las dos primeras líneas; el hito 3 agrega las otras tres. El demo_math actual ya imprime las cinco:

factorial(5) = 120
gcd(48, 18) = 6
isqrt(17) = 4
is_prime(17) = 1
is_prime(18) = 0

print_dec recibe un unsigned int; por eso la demo convierte los resultados con (unsigned int). Para estos valores la conversión es segura: el factorial negativo devuelve cero, el GCD de valores absolutos no es negativo y la raíz y la primalidad devuelven valores no negativos. No es una regla general para cualquier resultado negativo.

7. Las flags del Makefile: quién hace qué

Las flags del Makefile no son todas de la misma clase. Unas afectan la compilación, otras el enlace y otras el preprocesamiento. Tampoco son órdenes mágicas: cada una habilita o cambia una parte del proceso, y ninguna demuestra por sí sola que el programa sea correcto.

Flags de compilación y enlace del Makefile
FlagEtapaQué hace y qué no promete
-WallCompilaciónActiva un conjunto de advertencias frecuentes; no activa todas las advertencias posibles.
-WextraCompilaciónActiva advertencias adicionales a -Wall; no detecta todos los errores lógicos.
-WerrorCompilaciónConvierte en error cualquier advertencia que haya sido activada; no convierte en error lo que el compilador no diagnosticó.
-std=c11CompilaciónSelecciona el estándar ISO C11 (publicado en 2011) como dialecto formal del lenguaje C (soporta características como tipos de ancho fijo estandarizados, _Static_assert, etc.), desactivando extensiones incompatibles del compilador GNU pero permitiendo aquellas que no colisionan con el estándar.
-gCompilaciónIncluye información para depuración; no cambia por sí solo la lógica del programa.
-O0CompilaciónEs el nivel base de la receta normal, sin las optimizaciones de -O1 o -O2; no significa que el compilador no haga ninguna transformación menor.
-O2CompilaciónActiva un conjunto de optimizaciones en la receta opt; prioriza velocidad y no garantiza el menor tamaño posible.
-DNDEBUGPreprocesamientoDefine NDEBUG, que desactiva los assert de la biblioteca estándar; no desactiva validaciones propias que no usen assert.
-ffunction-sectionsCompilaciónPide poner cada función en una sección propia; por sí sola no hace que el linker descarte nada.
-fdata-sectionsCompilaciónPide poner cada dato o global en una sección propia; por sí sola tampoco descarta secciones.
-Wl,--gc-sectionsEnlacePasa --gc-sections al linker para descartar secciones no referenciadas; no decide si el código es correcto y puede eliminar lo que no tenga referencias.

El Makefile agrupa estas opciones en variables distintas:

CFLAGS    = -Wall -Wextra -Werror -std=c11 -g -O0
CFLAGS   += -ffunction-sections -fdata-sections
OPT_FLAGS = -Wall -Wextra -Werror -std=c11 -O2 -DNDEBUG
OPT_FLAGS += -ffunction-sections -fdata-sections
LDFLAGS   = -Wl,--gc-sections

CFLAGS se usa en la receta normal; OPT_FLAGS, en make opt y en los reportes de optimización; LDFLAGS, al linkear. La diferencia entre -O0 y -O2 no es «sin compilar» frente a «compilar»: en ambos casos se compila, pero cambia cuánto intenta transformar el compilador para mejorar el resultado.

La distinción entre -ffunction-sections y -Wl,--gc-sections es la más importante para leer el Makefile: la primera da al linker la posibilidad de tratar cada función por separado; la segunda es la que le pide descartar las secciones que no se usan. Una sin la otra no produce el mismo efecto. -Wl, significa «pasá lo que sigue al linker»; --gc-sections es una opción de ld, no de gcc.

El README pide agregar -Werror desde el hito 2. La lectura correcta es: las advertencias seleccionadas por -Wall y -Wextra pasan a impedir la compilación. Si una advertencia no está activada, -Werror no la convierte en error. Eso no garantiza que no queden errores lógicos.

Una compilación didáctica con las flags de la receta normal se leería así; no es una línea literal del Makefile:

$ gcc -Wall -Wextra -Werror -std=c11 -g -O0 \
    -ffunction-sections -fdata-sections \
    -Isrc/lib -Isrc/hal -Isrc/demo -Isrc/app -Isrc/platform \
    -c src/lib/mathlib.c -o build/lib/mathlib.o

Y el enlace incorpora la opción del linker, por ejemplo:

$ gcc -Wl,--gc-sections build/app/main.o build/lib/mathlib.o ... \
    -o build/building_process_demo

Los puntos suspensivos representan los demás objetos, la plataforma y las bibliotecas que agrega el Makefile; no son una línea literal. Lo importante es que las flags de compilación y las de enlace actúan en momentos distintos.

8. Por qué las cuatro funciones aparecen como T

El hito 2 pide verificar con nm que math_factorial y math_gcd aparecen como T. Al inspeccionar el objeto actual, también aparecen las dos funciones del hito 3:

$ nm build/lib/mathlib.o
0000000000000000 T math_factorial
0000000000000000 T math_gcd
0000000000000000 T math_is_prime
0000000000000000 T math_isqrt

T indica una definición en la sección de texto (código) con alcance global. Las cuatro funciones están definidas en mathlib.c sin static, así que son visibles para otros objetos. La minúscula t indicaría una definición local, por ejemplo una función static.

El consumidor es demo_math.o. Sus referencias aparecen como U porque ese objeto usa las funciones, pero no las define:

$ nm build/demo/demo_math.o
0000000000000000 T demo_math
                 U math_factorial
                 U math_gcd
                 U math_is_prime
                 U math_isqrt
                 U print_dec
                 U print_str

Al linkear, las U de demo_math.o se resuelven con las T de mathlib.o. Es la misma relación consumidor/proveedor del hito 1.

¿Por qué el header no alcanza para aportar las definiciones? Porque mathlib.h contiene los prototipos de las cuatro funciones, que le dicen al compilador cómo llamarlas, pero los cuerpos están en mathlib.c. La excepción es bit_set: su cuerpo sí está en el header como static inline, y por eso cada unidad de traducción que lo incluye puede obtener una copia local.

Los ceros repetidos: offset dentro de la sección vs. dirección final

En la salida de nm sobre un archivo objeto (.o), la primera columna no es todavía una dirección de memoria RAM, sino un desplazamiento u offset dentro de su sección. Como un .o es un objeto relocalizable, sus funciones no tienen una dirección definitiva asignada: la memoria final del programa recién la determina el linker al generar el ejecutable.

¿Por qué entonces aparecen todos ceros en mathlib.o? Debido a la opción -ffunction-sections:

  • Con -ffunction-sections (lo que hace este TP): el compilador aísla cada función en su propia sección individual (por ejemplo .text.math_factorial, .text.math_gcd, etc.). Dentro de su respectiva sección, cada función comienza en el byte 0. Por eso nm muestra 0000000000000000 para todas: indica que cada una está en el offset 0 de su propia sección. No significa que vayan a compartir la misma dirección de memoria.
  • Sin -ffunction-sections (compilación tradicional): todas las funciones del archivo se empaquetarían juntas en una única sección común llamada .text. En ese caso, la primera función estaría en el offset 0, pero la segunda empezaría donde termina la primera (por ejemplo en el offset 0x43), la tercera en 0x86, etc. Por lo tanto, sin esa flag los valores no serían todos cero, sino desplazamientos relativos crecientes dentro de esa única sección .text (pero seguirían sin ser direcciones finales de memoria hasta el linkeo).

Para comprobar que cada función tiene su propia sección y tamaños distintos, se puede usar objdump -h:

$ objdump -h build/lib/mathlib.o
Idx Name                  Size      VMA               File off
  3 .text.math_factorial  00000043  0000000000000000  00000040
  4 .text.math_gcd        00000043  0000000000000000  00000083
  5 .text.math_isqrt      00000055  0000000000000000  000000c6
  6 .text.math_is_prime   000000ba  0000000000000000  0000011b

La columna VMA (Virtual Memory Address) vale cero porque aún no hay direcciones de ejecución asignadas. En cambio, los tamaños (Size) son distintos: 0x43, 0x43, 0x55 y 0xba bytes. Con nm -S se puede ver el offset (0) junto al tamaño:

$ nm -S build/lib/mathlib.o
0000000000000000 0000000000000043 T math_factorial
0000000000000000 0000000000000043 T math_gcd
0000000000000000 00000000000000ba T math_is_prime
0000000000000000 0000000000000055 T math_isqrt

Recién al linkear, el linker coloca todas esas secciones en el ejecutable y les asigna sus direcciones finales de memoria:

$ nm build/building_process_demo | grep ' math_'
00000000000018e8 T math_factorial
000000000000192b T math_gcd
00000000000019c3 T math_is_prime
000000000000196e T math_isqrt

9. Una explicación oral posible

«mathlib.c define cuatro funciones globales: factorial, GCD, raíz entera y primalidad. mathlib.h declara sus prototipos, y demo_math.c las consume e imprime los resultados. Por eso nm build/lib/mathlib.o las muestra como T, mientras que demo_math.o las muestra como U hasta que el linker las resuelve».

10. Comprobá lo que aprendiste

P1. ¿Qué afirmaciones describen correctamente math_factorial?

Correctas: A y C. A: result empieza en 1 y el bucle arranca en 2. C: n < 0 devuelve 0 antes del bucle. B es falsa: el acumulador no empieza en cero y la operación es un producto, no una suma. D es falsa: 0! y 1! devuelven 1 porque el bucle no se ejecuta. La explicación se limita a entradas pequeñas; el desbordamiento no se analiza como garantía.

P2. En math_gcd(48, 18), ¿qué ocurre en cada iteración?

Correctas: B y C. En cada vuelta, tmp guarda el divisor anterior; b pasa a a % b; y a pasa a tmp. El bucle termina cuando b == 0, y entonces a es el último divisor no nulo. Para (48, 18) la cadena es (18, 12), (12, 6), (6, 0), y devuelve 6. A invierte los papeles: a no se reemplaza por el resto. D confunde normalizar los signos con devolver el valor absoluto de ambos; lo que devuelve es el GCD.

P3. ¿Qué describe el cálculo de math_isqrt(17)?

Correctas: A y C. A: n == 0 devuelve 0 antes de calcular x e y. C: todas las divisiones son enteras, así que se descarta la parte fraccionaria. B es falsa: el bucle sigue mientras y < x, no mientras y > n. D es falsa: la traza 17 → 9 → 5 → 4 termina devolviendo la parte entera de la raíz, no una aproximación mayor. La comparación final es 4 < 4, que es falsa.

P4. ¿Qué afirmaciones describen math_is_prime?

Correctas: A y C. A: n < 2 devuelve 0, así que negativos, cero y uno no se consideran primos. C: el bucle arranca en i = 5 y suma 6; prueba i e i + 2. B es falsa: 2 y 3 devuelven 1 por el caso n < 4. D es falsa: 6k ± 1 son candidatos, no una garantía; por ejemplo, 25 = 6 · 4 + 1 no es primo porque es divisible por 5.

P5. ¿Qué afirmaciones corresponden a mathlib.o y mathlib.h?

Correctas: A y D. A: T indica una definición en la sección de texto con alcance global. D: nm build/lib/mathlib.o muestra las cuatro funciones como T. B es falsa: t indicaría una definición local; U es el símbolo indefinido. C es falsa: mathlib.h contiene los prototipos de las cuatro funciones; los cuerpos están en mathlib.c. La excepción es bit_set, que sí tiene un cuerpo static inline en el header.
