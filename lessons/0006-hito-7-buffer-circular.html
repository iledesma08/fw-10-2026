Hito 7: buffer circular

Al terminar vas a poder seguir dónde se escribe y se lee cada byte, explicar el salto del índice 31 al 0 y justificar por qué la demo imprime ring: ABCDEFGHIJ.

1. Para qué sirve guardar datos en una cola

Imaginá que llegan varios bytes y el programa todavía está ocupado procesando el anterior. Hace falta un lugar para guardar los pendientes y recuperarlos en orden. Un buffer circular usa un array de tamaño fijo como una cola: se escribe por un extremo y se lee por el otro.

Productor       Cola         Consumidor
agrega A B C → [ A B C ] → obtiene A B C

FIFO: primero en entrar, primero en salir.

Puede servir para desacoplar momentáneamente la llegada de datos de su procesamiento. No permite acumular una cantidad ilimitada: si el productor agrega más rápido de lo que el consumidor retira durante demasiado tiempo, el buffer se llena.

¿Por qué circular? Al llegar al final del array, el índice vuelve al principio y reutiliza lugares que ya quedaron libres. No hay que desplazar todos los bytes para sacar el primero. Los datos no giran físicamente: avanzan los índices.

El caso real y el caso del TP

Una aplicación podría usar una cola para datos recibidos por UART. Pero en el hito 7 del TP la demo agrega las letras con un bucle y después las retira con otro; no hay una UART alimentando automáticamente este buffer. Esta implementación tampoco incluye sincronización para hilos o interrupciones concurrentes.

Seguimos el código existente sin modificar ni recompilar C. Las salidas se explican mediante trazas, no son una nueva ejecución del binario.

2. Capacidad, índices y cantidad de datos

// hal_ring.h:14–22 (sin los comentarios)
#define RING_BUF_SIZE 32

typedef struct {
  uint8_t data[RING_BUF_SIZE];
  uint16_t head;
  uint16_t tail;
  uint16_t count;
} ring_buf_t;
Los cuatro campos del buffer
CampoQué significa
data[32]Almacena los bytes en índices de 0 a 31; el almacenamiento vive dentro de la estructura.
headÍndice del próximo lugar donde escribir, si no está lleno.
tailÍndice del próximo byte que se leerá, si no está vacío.
countCantidad de bytes pendientes, de 0 a 32 inclusive.

head y tail no son punteros: son números usados como índices del array. uint8_t y uint16_t indican enteros sin signo de 8 y 16 bits, no de 8 y 16 bytes. No se usa malloc.

Esto no es un string: no se reserva lugar para NUL y un byte cero es un dato válido. Pueden usarse las 32 posiciones. count permite distinguir dos casos en los que los índices podrían ser iguales:

Después de inicializar:      head = 0, tail = 0, count = 0   → vacío
Después de agregar 32 bytes: head = 0, tail = 0, count = 32  → lleno

Por eso head == tail no basta para decidir si está vacío. Los helpers del header consultan la ocupación:

static inline int ring_is_empty(const ring_buf_t *rb) {
  return rb->count == 0;
}

static inline int ring_is_full(const ring_buf_t *rb) {
  return rb->count >= RING_BUF_SIZE;
}

En un buffer válido, lleno significa count == 32; el código usa >=. Estas funciones devuelven una condición (verdadero o falso), mientras que push y pop devuelven un estado de éxito o error. No hay que confundir esos contratos.

3. Inicializar, agregar y retirar

// hal_ring.c:10–17
void ring_init(ring_buf_t *rb) {
  for (uint16_t i = 0; i < RING_BUF_SIZE; i++)
    rb->data[i] = 0U;

  rb->head = 0U;
  rb->tail = 0U;
  rb->count = 0U;
}

rb apunta al buffer que se modifica. Esta implementación borra los 32 datos y reinicia los índices y la ocupación. Lo que indica que está vacío es count = 0, no que todos los datos sean cero.

Push: encolar un byte

int ring_push(ring_buf_t *rb, uint8_t byte) {
  if (ring_is_full(rb))
    return -1;

  rb->data[rb->head] = byte;
  rb->head = (uint16_t)((rb->head + 1U) % RING_BUF_SIZE);
  rb->count++;

  return 0;
}

Primero comprueba si hay lugar. Si está lleno, devuelve -1 sin escribir ni cambiar los índices o count: no sobrescribe el dato más antiguo. Si hay lugar, escribe en data[head], avanza head, incrementa count y devuelve 0 (éxito).

Pop: desencolar un byte

int ring_pop(ring_buf_t *rb, uint8_t *byte) {
  if (ring_is_empty(rb))
    return -1;

  *byte = rb->data[rb->tail];
  rb->tail = (uint16_t)((rb->tail + 1U) % RING_BUF_SIZE);
  rb->count--;

  return 0;
}

Si está vacío, devuelve -1 sin leer el array ni escribir en la variable de salida. Si hay datos, copia el byte de data[tail] al lugar indicado por el puntero, avanza tail, disminuye count y devuelve 0.

uint8_t recibido;
int estado = ring_pop(&sim_ring, &recibido);
// estado: 0 si pudo sacar un byte, -1 si estaba vacío.
// recibido: contiene el dato nuevo solo si estado == 0.

Hay dos resultados distintos: el return comunica el estado; el puntero de salida entrega el byte. &recibido es la dirección de la variable; *byte = ... escribe en esa variable del llamador. Si falla, no entrega un dato nuevo: no hay que usar un valor previo o sin inicializar como si acabara de recibirse.

pop no borra la celda del array. Retirar un dato significa que ya no cuenta como pendiente y su lugar puede reutilizarse. Los índices y count, no el aspecto del array, determinan qué datos siguen en la cola.

Contrato del código: el buffer debe estar inicializado y conservar un estado válido. Los punteros deben ser válidos; para un pop exitoso, el puntero de salida debe permitir escribir un byte. Estas funciones no validan cualquier puntero ni coordinan accesos concurrentes.

4. Seguir los índices en lugar de mover los datos

push('C')312B, C
pop → 'B'321C
pop → 'C'330Ninguno.

Al final, A, B y C pueden seguir escritos en las primeras celdas, pero ya no están pendientes. Otro pop devuelve -1, aunque queden esos valores viejos en memoria.

Por qué el índice 31 vuelve al 0

% calcula el resto de una división entera. Se aplica al siguiente índice:

(30 + 1) % 32 = 31
(31 + 1) % 32 =  0    vuelve al inicio del array
( 0 + 1) % 32 =  1

El índice no llega a usarse como 32: el resto lo devuelve al rango 0–31. Imaginá un estado válido con head = 31, tail = 30, count = 1 y un byte X pendiente en el índice 30. Se puede llegar ahí agregando 31 bytes desde vacío y retirando 30, siendo X el último de esos 31:

Una escritura y dos lecturas cerca del final

Estado inicial del ejemploX está en 30.31301

El salto al principio no rompe el orden FIFO ni mueve los datos. Las comprobaciones de lleno y vacío, junto con count, impiden reutilizar un lugar todavía ocupado o leer un dato que ya no está pendiente.

5. Por qué se imprime ABCDEFGHIJ

// demo_embedded.c:45–53
ring_init(&sim_ring);
for (uint8_t i = 0U; i < 10U; i++)
  (void)ring_push(&sim_ring, (uint8_t)('A' + i));

print_str("ring: ");
while (ring_pop(&sim_ring, &byte) == 0)
  print_chr((char)byte);
print_str("\n");

La instancia static ring_buf_t sim_ring está declarada fuera de las funciones. Esta demo la reinicia explícitamente con ring_init antes de usarla. En el entorno ASCII del TP, sumar de 0 a 9 a 'A' genera las letras A a J.

  • Entran diez bytes en un buffer vacío con capacidad de 32: los diez push tienen éxito. Quedan head = 10, tail = 0 y count = 10.
  • (void)ring_push(...) descarta intencionalmente el estado devuelto. No significa que la función no devuelva nada. En otra situación habría que manejar la posibilidad de lleno.
  • El while llama a pop y solo imprime si devuelve 0. Retira A, B, C… J. Al quedar vacío, una llamada más devuelve −1 y termina el bucle sin imprimir un byte extra.
  • Al final quedan head = 10, tail = 10 y count = 0. Los índices no tienen que ser cero para que esté vacío.
ring: ABCDEFGHIJ

Es la salida esperada por la consigna y derivada del código, no una ejecución nueva. Se imprime por la consola host mediante print_chr; no se envían automáticamente esas letras por la UART simulada. El uso posterior del ring para una trama con CRC corresponde al hito 9.

Una explicación oral posible

«El buffer tiene 32 lugares. Head indica dónde agrego, tail dónde retiro y count cuántos bytes quedan. Push y pop avanzan sus índices con resto 32 para volver al principio. Count distingue lleno de vacío aunque los índices coincidan. Pop devuelve el estado y entrega el byte mediante un puntero. Como es FIFO, las diez letras salen en el mismo orden en que entraron».

6. Comprobá lo que aprendiste

P1. ¿Qué representan los campos del buffer?

Correctas: A y D. head es el próximo índice de escritura, tail el de lectura y count la ocupación. B intercambia las funciones de los índices. C es falsa: este buffer contiene bytes, no un string; puede usar los 32 lugares y almacenar un byte cero.

P2. ¿Cómo se distinguen lleno y vacío?

Correctas: B y C. Al inicializar, ambos índices valen 0 y count = 0; después de 32 inserciones sin retirar, ambos vuelven a coincidir y count = 32. A ignora esa ambigüedad. D es falsa: un cero puede ser un byte válido; el contenido de las celdas no indica cuáles están ocupadas.

P3. ¿Qué hacen el avance circular y los controles de capacidad?

Correctas: A y C. (30 + 1) % 32 = 31 y (31 + 1) % 32 = 0, por lo que B es falsa. Si está lleno, push retorna −1 antes de modificar el buffer. D es falsa: pop avanza tail y disminuye count, sin mover los demás bytes.

P4. ¿Cómo entrega ring_pop su resultado?

Correctas: B y D. Un pop exitoso devuelve 0, copia el byte a *byte y actualiza tail y count. A confunde estado con dato. C es falsa: si está vacío retorna −1 antes de escribir en el parámetro de salida.

P5. ¿Por qué la demo imprime exactamente ABCDEFGHIJ?

Correctas: A y D. Hay lugar para las diez letras y la cola conserva el orden FIFO. El while solo imprime tras pop == 0; cuando está vacío, termina sin imprimir datos viejos. B describe una inversión que no ocurre. C es falsa: (void) solo descarta el estado; no impide que otra inserción pueda fallar si el buffer está lleno.
