Hitos 8 y 9: timer y trama

Vas a poder explicar cómo el timer acumula ticks y cómo la demo arma, transporta por un buffer local y comprueba una trama de seis bytes.

1. Un contador de tiempo sin reloj físico

Una aplicación puede necesitar medir tiempo transcurrido, por ejemplo para saber cuántos milisegundos pasaron desde el inicio. Este módulo ofrece una interfaz pequeña: inicializar, avanzar un tick y consultar el contador. En este ejercicio es un contador de software; no lee un periférico ni mide el tiempo real por sí mismo. La demo imprime la salida esperada timer_ms: 3, derivada de tres incrementos tras inicializar.

// hal_timer.c
static uint32_t timer_ms;

void timer_init(void) { timer_ms = 0U; }
void timer_tick(void) { timer_ms++; }
uint32_t timer_get_ms(void) { return timer_ms; }

static limita el nombre timer_ms a este archivo: otros módulos no lo modifican directamente. La interfaz pública está declarada en hal_timer.h. Inicializar pone el estado a cero; cada llamada a timer_tick suma uno; consultar devuelve el acumulado.

El comentario del módulo define un tick como 1 ms, pero tres llamadas no equivalen necesariamente a tres milisegundos físicos: aquí la demo invoca las funciones consecutivamente y no espera ni configura una interrupción periódica. El resultado lógico es tres ticks acumulados.

timer_init();       // timer_ms = 0
timer_tick();       // timer_ms = 1
timer_tick();       // timer_ms = 2
timer_tick();       // timer_ms = 3
timer_get_ms();     // devuelve 3

2. Qué problema resuelve una trama

Al recibir bytes, el programa necesita reconocer dónde empieza una unidad de datos y comprobar si su contenido coincide con lo esperado. Una trama fija agrupa bytes con una estructura conocida: sincronismo, datos y comprobación. Payload significa los datos útiles que la trama transporta, aquí cuatro bytes; además hay un byte de sincronismo y un byte CRC. El buffer circular sirve como almacenamiento temporal entre la inserción y la extracción de esos bytes.

Índice:    0    1    2    3    4    5
Trama:   AA   01   02   03   04   32
         └sync┘ └── payload ──┘ └CRC┘

El CRC de este payload es 0x32, según el algoritmo del TP, que empieza en STR_CRC8_INIT (0xFF) y usa el polinomio 0x07. CRC es una comprobación de errores, no una autenticación ni una prueba universal de que los datos estén intactos: distintos errores pueden no detectarse.

Extracto: construir y pasar los seis bytes

El bloque reúne declaraciones y operaciones de demo_embedded.c para seguir el recorrido; no es un archivo C completo independiente.

#define FRAME_SIZE 6U
static ring_buf_t sim_ring;
uint8_t frame[FRAME_SIZE];
uint8_t received[FRAME_SIZE] = {0U};

static const uint8_t payload[] = {0x01U, 0x02U, 0x03U, 0x04U};
frame[0] = 0xAAU;
for (size_t i = 0; i < sizeof(payload); i++)
  frame[1U + i] = payload[i];
crc_expected = str_crc8(payload, sizeof(payload));
frame[FRAME_SIZE - 1U] = crc_expected;

ring_init(&sim_ring);
frame_ok = 1;
for (size_t i = 0; i < FRAME_SIZE; i++) {
  if (ring_push(&sim_ring, frame[i]) != 0)
    frame_ok = 0;
}
for (size_t i = 0; i < FRAME_SIZE; i++) {
  if (ring_pop(&sim_ring, &received[i]) != 0)
    frame_ok = 0;
}

El ring_init ocurre antes de meter la trama: reinicia el estado del buffer. Los seis push y seis pop comprueban sus retornos; si cualquiera falla, frame_ok queda en cero. En esta demo vacía, de capacidad 32, esas operaciones deben caber. Esto describe este recorrido concreto, no valida cualquier trama, puntero o estado posible.

Importante: el ring usado aquí es memoria local del programa. Aunque la demo también simula registros UART en otra parte, este código no envía automáticamente la trama por UART ni la recibe desde un cable.

3. Validar cabecera y CRC

if (frame_ok && received[0] == 0xAAU) {
  crc_received = str_crc8(&received[1], FRAME_SIZE - 2U);
  if (crc_received != received[FRAME_SIZE - 1U])
    frame_ok = 0;
} else {
  frame_ok = 0;
}

La expresión usa evaluación de cortocircuito con &&: si frame_ok es cero, C no evalúa la expresión siguiente ni accede a received[0]. Si es distinto de cero, compara el byte de índice 0 con 0xAA. Para recalcular el CRC pasa la dirección de received[1] y longitud FRAME_SIZE - 2, que vale 4: recorre los cuatro bytes del payload y excluye sincronismo y CRC final. Finalmente compara el CRC calculado con el recibido en índice 5.

Si la cabecera, las operaciones del ring o la comparación CRC fallan, el flujo previsto imprime frame: error. El programa no incluye aquí un receptor genérico de tramas: conoce el tamaño y la estructura de esta demostración.

Una explicación oral posible

«El timer guarda un contador estático privado: init lo pone a cero, tick incrementa uno y get lo devuelve. En la demo tres llamadas producen tres ticks lógicos, no necesariamente tres milisegundos físicos. La trama tiene seis bytes: sincronismo AA, cuatro bytes de payload y CRC. Se reinicia el ring, se comprueban inserciones y retiros, y se verifica cabecera y CRC del payload, sin sincronismo ni byte CRC».

4. Comprobá lo que aprendiste

P1. ¿Qué función cumple cada llamada del timer?

Correcta: A. timer_init asigna cero. B: timer_tick incrementa. C: timer_get_ms devuelve el acumulado, no espera. D: static limita timer_ms a su archivo.

P2. ¿Qué se puede concluir de tres llamadas a timer_tick?

Correcta: A. Tres incrementos luego de timer_init dejan el valor lógico en tres. B: no hay espera ni fuente periódica. C: solo la inicialización pone cero. D: la consulta no modifica estado.

P3. ¿Cómo se organiza la trama del ejemplo?

Correctas: A y C. La trama suma un byte de sync, cuatro de payload y uno CRC: seis en total. B invierte los extremos. D confunde la longitud del payload con el tamaño total de la trama.

P4. ¿Qué bytes cubre el CRC recalculado?

Correctas: B y D. La dirección es &received[1] y la longitud es 6 - 2 = 4. A incluye bytes que no forman parte del cálculo definido; C apunta al byte de sincronismo, no al payload.

P5. ¿Qué describe correctamente la demo de transporte?

Correctas: A y C. ring_init precede a los bucles y los estados no exitosos ponen frame_ok en cero. B es falsa: el ring es memoria local, no un transporte UART automático. D es falsa: CRC no autentica ni detecta necesariamente cualquier alteración.
