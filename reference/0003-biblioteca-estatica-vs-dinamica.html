Bibliotecas en C: estáticas (.a) vs. dinámicas (.so)

Comparación técnica de mecanismos, tiempos de resolución (build time vs. runtime), consumo de memoria, comandos del toolchain (ar, gcc -shared, ldd) y su impacto en sistemas embebidos frente a sistemas operativos de propósito general.

En esta hoja: Concepto esencial · Mecanismo de funcionamiento · Tabla comparativa · Comandos y generación · Criterio en sistemas embebidos · Caso concreto del TP3

1. Concepto esencial: ¿cuándo y cómo se unen al ejecutable?

Una biblioteca es una colección de código precompilado (funciones, estructuras, datos) pensada para ser reutilizada por múltiples programas o módulos sin tener que recompilar sus archivos fuente (.c) cada vez.

La diferencia fundamental entre una biblioteca estática y una dinámica radica en en qué momento y de qué manera el código de la biblioteca se conecta con el programa consumidor:

  • Biblioteca estática (.a en Linux, .lib en Windows): se vincula durante el tiempo de compilación/enlace (build time). El linker (ld) copia físicamente las funciones requeridas directamente dentro del archivo binario ejecutable final.
  • Biblioteca dinámica o compartida (.so en Linux, .dll en Windows): se vincula en dos etapas. En build time solo se verifica que los símbolos existan y se anota su nombre en el ejecutable; la resolución real y la carga del código en memoria ocurren en tiempo de ejecución (runtime) mediante el cargador dinámico del sistema operativo (ld.so).

2. Mecanismo de funcionamiento

Biblioteca estática (Static Archive)

Tiempo de compilación:
 [ main.o ] + [ libutils.a (mathlib.o, strutils.o...) ]
                     │
              (Linker / ld)
                     │  Copia el código de los miembros necesarios
                     ▼
             [ ejecutable final ] (Autónomo: contiene el código de la biblioteca)

Un archivo .a (archive) es simplemente un empaquetado (como un archivo comprimido tar o zip, pero sin compresión obligatoria) creado con la herramienta ar. Contiene adentro una colección de archivos objeto relocalizables (.o) acompañados de una tabla de símbolos o índice.

Cuando el linker procesa -lutils:

  1. Revisa qué referencias no resueltas (símbolos U) tiene pendientes en los objetos previos.
  2. Examina el índice de libutils.a para ver qué miembros (.o) definen esos símbolos.
  3. Extrae del archivo solo los miembros .o que aportan símbolos necesarios y los incorpora al ejecutable. Si se combina con -ffunction-sections y -Wl,--gc-sections, el linker puede descartar además funciones individuales no alcanzadas.
  4. Una vez generado el ejecutable, la biblioteca .a ya no se necesita para ejecutar el programa.

Biblioteca dinámica o compartida (Shared Object)

Tiempo de compilación:
 [ main.o ] + [ libutils.so ]
                     │
              (Linker / ld)
                     │  Verifica símbolos y anota dependencias (DT_NEEDED)
                     ▼
             [ ejecutable final ] (Contiene solo referencias al nombre 'libutils.so')

Tiempo de ejecución (Runtime):
 Al ejecutar ./programa:
    1. El OS invoca al cargador dinámico (ld-linux.so).
    2. ld.so busca 'libutils.so' en el disco (/lib, /usr/lib, LD_LIBRARY_PATH).
    3. Carga el código de libutils.so en memoria RAM (compartido entre procesos).
    4. Resuelve las direcciones de memoria de las funciones invocadas.

El ejecutable resultante es más liviano porque no contiene el código máquina de la biblioteca. Sin embargo, para ejecutarse depende estrictamente de que el archivo .so exista en el sistema operativo en una ruta donde el cargador dinámico pueda encontrarlo.

3. Tabla comparativa detallada

Diferencias clave entre bibliotecas estáticas y dinámicas
Criterio Biblioteca estática (.a) Biblioteca dinámica (.so / .dll)
Momento de enlace Build time (al momento de linkear con gcc / ld). Runtime (al momento de cargar y ejecutar el binario).
Herramienta de empaquetado ar rcs libnombre.a objeto1.o objeto2.o gcc -shared -fPIC -o libnombre.so objeto1.o...
Tamaño del ejecutable Mayor: el código de las funciones usadas se copia físicamente adentro del binario. Menor: solo almacena referencias y metadatos sobre qué biblioteca externa necesita.
Consumo de memoria RAM Si 10 programas usan la misma biblioteca estática, el código se duplica 10 veces en RAM. Eficiente: el código de solo lectura (.text) se carga una vez en RAM física y se comparte entre múltiples procesos.
Independencia / Portabilidad Alta: el ejecutable no falla por bibliotecas faltantes o versiones incompatibles en la máquina destino. Dependiente: requiere que el host tenga instalada la versión exacta o compatible de la biblioteca (evita o sufre el "dependency hell").
Actualizaciones y parches Si se corrige un bug en la biblioteca, es obligatorio volver a linkear todos los ejecutables. Basta con reemplazar el archivo .so en el sistema; todos los programas se benefician sin recompilarse.
Código independiente de posición (PIC) No suele requerir -fPIC (se reubica en direcciones fijas durante el enlace). Obligatorio: debe compilarse con -fPIC (Position Independent Code) para poder cargarse en cualquier dirección de memoria virtual.
Tiempo de arranque Instantáneo: no hay resolución de símbolos ni carga diferida al iniciar el proceso. Leve sobrecarga inicial: el sistema operativo debe localizar los archivos .so y reubicar símbolos antes de dar control al main.

4. Comandos del Toolchain para crear e inspeccionar

Creación

# 1. Crear biblioteca estática:
$ gcc -c modulo1.c modulo2.c               # Genera modulo1.o modulo2.o
$ ar rcs libmiutil.a modulo1.o modulo2.o   # Empaqueta e indexa en .a

# 2. Crear biblioteca dinámica:
$ gcc -fPIC -c modulo1.c modulo2.c         # Compila con código independiente de posición
$ gcc -shared -o libmiutil.so modulo1.o modulo2.o  # Enlaza como objeto compartido

Inspección

Para ver qué miembros u objetos tiene una biblioteca estática:

$ ar t libutils.a                         # Lista los miembros (.o) contenidos
$ nm -A --defined-only libutils.a         # Muestra símbolos definidos indicando miembro

Para inspeccionar qué bibliotecas dinámicas necesita un ejecutable en Linux:

$ ldd build/building_process_demo

Ejemplo de salida de ldd:

linux-vdso.so.1 (0x00007ffd...)
libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f34...)
/lib64/ld-linux-x86-64.so.2 (0x00007f34...)

El comando ldd consulta la sección dinámica del binario (.dynamic) e imprime la ruta resuelta para cada dependencia compartida.

5. Criterio de elección en sistemas embebidos (Bare-metal y RTOS)

En el desarrollo de firmware para microcontroladores (como Cortex-M, AVR, PIC, RISC-V), casi universalmente se utilizan bibliotecas estáticas (.a) y se descartan las dinámicas por razones arquitectónicas concretas:

  1. Ausencia de Sistema Operativo y Cargador Dinámico: En sistemas bare-metal no existe un kernel de Linux ni un programa ld.so que pueda interpretar el formato ELF en tiempo de ejecución, leer un sistema de archivos y mapear páginas en memoria.
  2. Falta de MMU (Memory Management Unit): Las bibliotecas dinámicas requieren memoria virtual y MMU para proyectar el mismo segmento de código .text en los diferentes espacios de direcciones de múltiples procesos. Los microcontroladores suelen tener solo MPU (Memory Protection Unit) o memoria física plana compartida.
  3. Determinismo y Fiabilidad: En firmware de tiempo real no se puede tolerar la latencia variable de resolver símbolos en runtime o el riesgo de que el dispositivo no arranque por una falla al cargar una biblioteca externa.
  4. Optimización y Descarte de Código Muerto (LTO y Dead Code Elimination): Al enlazar estáticamente con -ffunction-sections -fdata-sections y -Wl,--gc-sections, el linker elimina toda función de la biblioteca estática que la aplicación no llame jamás, ahorrando valiosa memoria Flash (ROM). Con bibliotecas dinámicas, el .so completo debe residir en el sistema.

¿Cuándo se usan bibliotecas dinámicas en embebidos? Únicamente en plataformas de gama alta con sistemas tipo Embedded Linux (por ejemplo routers, gateways o dispositivos con Raspberry Pi, BeagleBone, NXP i.MX), donde hay un procesador con MMU, gigabytes de almacenamiento y múltiples aplicaciones concurrentes compartiendo servicios.

6. El caso concreto de este TP3

En el hito 11 del TP se construye build/libutils.a. Es fundamental entender dos precisiones técnicas habituales en las preguntas de defensa:

  1. Enlazar una biblioteca estática propia no hace que el ejecutable sea 100% estático:
    Aunque libutils.a se enlaza de forma estática (incorporando mathlib.o, strutils.o, etc., al ejecutable), el binario final sigue siendo un ejecutable dinámico en el host Linux porque utiliza funciones del sistema operativo provistas por la biblioteca estándar de C compartida (libc.so, por ejemplo __stack_chk_fail o __ctype_b_loc). Para hacer un ejecutable totalmente estático que no dependa de ningún .so se requeriría el flag -static de GCC.
  2. El orden de enlace con bibliotecas estáticas es estricto:
    En GCC, el linker recorre los archivos en la línea de comando de izquierda a derecha. Por eso en el Makefile los objetos consumidores (APP_OBJS) se ubican antes de -Lbuild -lutils. Si se colocara -lutils antes de los objetos que lo necesitan, el linker no vería referencias pendientes en ese momento y descartaría los miembros de la biblioteca, provocando errores de undefined reference posteriores.
