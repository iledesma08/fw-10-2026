Secciones de memoria: text, data, bss, heap y stack

Guía conceptual y práctica sobre la distribución de memoria (layout), qué representa cada sección, dónde residen en hardware (Flash vs. RAM) y cómo se inspeccionan con las herramientas del curso.

En esta hoja: Mapa de memoria · Text, Data y BSS · Heap y Stack · Flash frente a RAM · Comandos de inspección

1. El mapa de memoria (Memory Layout)

Todo programa en ejecución organiza su espacio de direcciones en diferentes regiones o segmentos con propósitos y permisos específicos (lectura, escritura, ejecución):

En este esquema se distinguen dos grandes grupos:

  • Secciones estáticas (definidas durante la compilación y enlace): .text, .rodata, .data y .bss. Su tamaño total queda fijado al construir el binario.
  • Regiones dinámicas (gestionadas en tiempo de ejecución): Heap y Stack. No ocupan espacio dentro del archivo ejecutable en disco.

2. Diferencia entre text, data y bss

.text (Código de instrucciones)

  • Qué almacena: las instrucciones binarias en código máquina correspondientes a todas las funciones compiladas (como main, math_factorial, print_str, etc.).
  • Permisos: Solo lectura y ejecución (RX). No se puede escribir en tiempo de ejecución para evitar que un programa modifique su propio código o sufra inyecciones de código.
  • Tamaño en el binario: ocupa espacio físico exacto en el archivo ejecutable.

.rodata (Read-Only Data)

  • Qué almacena: constantes globales que nunca deben modificarse en tiempo de ejecución, literales de strings (como "Hello, World!\n") y tablas fijas. En el TP, arrays como static const char PROGRAM_NAME[] = "building-process"; se ubican en esta sección.
  • Permisos: Solo lectura (R).
  • Relación con size: la columna Berkeley text de GNU size suma tanto .text como .rodata y otras secciones de solo lectura.

.data (Datos globales inicializados)

  • Qué almacena: variables globales o estáticas que fueron inicializadas explícitamente en el código con un valor distinto de cero (por ejemplo: int contador = 10;).
  • Permisos: Lectura y escritura (RW).
  • Tamaño en el binario: ocupa espacio físico en el archivo ejecutable, porque los valores con los que arranca deben estar guardados en el archivo.
  • En el TP: el código de aplicación del TP3 no define variables globales inicializadas con valores distintos de cero (por eso .data de nuestra app mide cero, y solo el runtime de C/ELF agrega algunos bytes internos).

.bss (Datos globales en cero o sin inicializar)

  • Qué almacena: variables globales o estáticas que no fueron inicializadas explícitamente en el código C, o que fueron inicializadas explícitamente en cero (por ejemplo: int buffer[100]; o static int estado = 0;).
  • Origen del nombre: Block Started by Symbol (un operador histórico de ensamblador).
  • Permisos: Lectura y escritura (RW).
  • Tamaño en el binario: 0 bytes de datos en el archivo ejecutable. El binario solo guarda un número de 4 u 8 bytes que indica cuántos bytes de BSS necesita el programa al arrancar. Esto ahorra mucho espacio en disco o memoria Flash: un array de 1 MB sin inicializar no agrega 1 MB al archivo compilado.
  • En el TP: las estructuras de simulación como sim_uart (20 bytes), sim_ring (38 bytes) y el acumulador timer_ms (4 bytes) son variables estáticas sin inicializar, por lo que residen en BSS.

3. Qué son el Heap y el Stack

¿Cuál es el Heap?

El Heap (o montículo) es la región de memoria RAM destinada a la asignación dinámica solicitada explícitamente por el programador en tiempo de ejecución mediante funciones como malloc(), calloc() o realloc(), y liberada con free().

  • Ubicación: comienza justo al terminar la sección .bss y crece hacia arriba (hacia direcciones de memoria más altas).
  • Vida útil: los bloques en el heap persisten hasta que se llama a free() o finaliza el proceso; no se destruyen al retornar de una función.
  • En sistemas embebidos: en firmware bare-metal y sistemas de tiempo real críticos (médicos, automotrices, aeroespaciales) se desaconseja o prohíbe el uso del heap para evitar la fragmentación de la memoria RAM, fugas de memoria (memory leaks) y tiempos de asignación impredecibles. En este TP3 no se utiliza el heap.

¿Qué es el Stack?

El Stack (o pila de llamadas) es la región de memoria RAM administrada automáticamente por la CPU y el compilador a través del registro Stack Pointer (SP).

  • Qué almacena: variables locales automáticas de las funciones, direcciones de retorno cuando se llama a una función, registros salvados y parámetros pasados por pila.
  • Ubicación y crecimiento: en x86_64 y ARM Cortex-M, el stack comienza en el extremo más alto de la memoria RAM disponible y crece hacia abajo (hacia direcciones más bajas, acercándose al heap).
  • Vida útil: cuando una función es invocada se crea su marco de pila (stack frame); al retornar de la función, el puntero de pila retrocede y esa memoria se reutiliza de inmediato.
  • Stack Overflow: ocurre cuando llamadas anidadas muy profundas (recursión infinita) o buffers locales excesivamente grandes superan el límite del stack y colisionan con el heap o las variables globales, provocando un fallo catastrófico (Segmentation Fault en Linux o un HardFault en microcontroladores).

4. ¿Están en Flash o en RAM?

La respuesta depende de si consideramos un microcontrolador embebido (como ARM Cortex-M) o un sistema operativo host (como Linux en una notebook):

Distribución física de las secciones de memoria
Sección / RegiónEn microcontroladores embebidosEn Linux (Host)Persistencia
.text Flash (ROM): se ejecuta directo desde Flash (XIP: eXecute In Place). Memoria Virtual (RAM): mapeado desde el archivo ELF con páginas Read-Only + Execute. No volátil (sobrevive al corte de energía).
.rodata Flash (ROM): constantes y tablas fijas. Memoria Virtual (RAM): páginas Read-Only mapeadas del ejecutable. No volátil.
.data Flash (carga) → RAM (ejecución): guardada en Flash y copiada a RAM al arrancar. RAM (Memoria Virtual): cargada desde el ejecutable con páginas Read/Write. Volátil (en RAM durante ejecución).
.bss RAM: no ocupa espacio en Flash; se llena con ceros al arrancar. RAM (Memoria Virtual): páginas anónimas puestas a cero por el kernel al cargarse. Volátil.
Heap RAM: entre el fin de BSS y el Stack. RAM (Memoria Virtual): administrado por la libc mediante brk o mmap. Volátil.
Stack RAM: desde el tope superior de la RAM física hacia abajo. RAM (Memoria Virtual): asignado por el kernel para el hilo principal del proceso. Volátil.
El código de arranque (Startup Code / Reset Handler)

Cuando un microcontrolador se enciende, la memoria RAM contiene basura aleatoria. Antes de ejecutar main(), el código de arranque (ensamblador de inicio o crt0.s) realiza dos tareas obligatorias por el estándar de C:

  1. Copiar .data: copia los valores iniciales de las variables globales desde la Flash (dirección LMA, Load Memory Address) hacia sus direcciones en RAM (dirección VMA, Virtual/Execution Memory Address).
  2. Poner a cero .bss: ejecuta un bucle que llena de ceros (0x00) toda la región de memoria RAM reservada para BSS.

5. Cómo inspeccionar estas secciones con comandos

Para ver el resumen agregado de secciones en un ejecutable o biblioteca:

$ size build/building_process_demo
   text    data     bss     dec     hex filename
   7200     616     112    7928    1ef8 build/building_process_demo

Para inspeccionar las secciones individuales y saber cuáles se cargan en memoria:

$ size -A build/building_process_demo
$ readelf -S -W build/building_process_demo

En la salida de readelf -S, la bandera A (Alloc) indica que la sección se cargará en la memoria del programa al ejecutarse (como .text, .rodata, .data y .bss). Las secciones que no tienen la bandera A (como .debug_info o tablas de comentarios) se quedan únicamente en el archivo en disco y no consumen memoria RAM ni memoria cargada.
